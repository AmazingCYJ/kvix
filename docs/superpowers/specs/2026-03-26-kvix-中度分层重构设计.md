# kvix 中度分层重构设计

## 1. 背景

当前本机存在一个 Bitcask 风格的 KV 存储项目，源目录为 `/Users/amazing/code/go/bitcask-my`。该项目已经具备以下能力：

- 基础 KV 数据读写
- 批量写入
- 迭代器
- Merge 压缩整理
- 多种索引实现
- 基于 KV 引擎封装的 Redis 风格数据结构
- 基于 Fiber 的 HTTP 示例接口

当前项目的主要问题不在于功能缺失，而在于代码的可读性、注释完整度、模块职责表达、文档覆盖率和命名一致性仍然不够理想。尤其是：

- 根模块中的核心文件职责偏重，阅读成本较高
- 注释风格不统一，很多函数缺少明确的用途和参数解释
- 一些函数内部虽然逻辑完整，但缺少按步骤分层说明
- 子模块缺少系统性的模块级 README
- 项目名称仍为 `bitcask-my`，与目标仓库名 `kvix` 不一致

因此需要在**不改变项目整体逻辑**的前提下，对项目进行一次**中度分层重构**，并将重构结果放置到新目录 `/Users/amazing/code/go/kvix` 中，以新仓库形式维护。

## 2. 重构目标

本次重构的目标如下：

### 2.1 命名统一

- 将项目名称从 `bitcask-my` 全量调整为 `kvix`
- 将 `go.mod` 中的模块名改为 `kvix`
- 将仓内 import 路径改为 `kvix/...`
- 将根包名从 `bitcaskmy` 调整为 `kvix`
- 将文档、示例、HTTP 应用名等对外命名同步改为 `kvix`

### 2.2 可读性提升

- 为核心函数和公开函数补齐详细中文注释
- 为中长函数增加按执行目的组织的中文步骤注释
- 对超长文件和职责混杂的实现做适量拆分
- 统一代码排版、命名表达和 import 组织方式

### 2.3 模块文档完善

- 为根目录和各核心模块补充 `README.md`
- README 重点覆盖设计思路、职责边界、关键流程和使用方式
- 确保读者可以在不深入源码的情况下先建立整体理解

### 2.4 逻辑保持不变

- 不改变原有存储格式
- 不改变原有 API 语义
- 不改变原有索引行为
- 不改变原有 Merge 逻辑
- 不改变原有 Redis 风格数据结构语义
- 不主动引入与本次可读性重构无关的新特性

## 3. 非目标

以下内容明确不属于本次重构范围：

- 不重写底层存储引擎
- 不重新设计数据文件编码格式
- 不对外新增一套新的 API 体系
- 不引入大型框架或全新的分层架构范式
- 不将项目彻底改造成 `internal/` 深层分层模式
- 不顺手修复与重构目标无关的历史行为差异，除非该问题直接阻塞迁移或编译

## 4. 当前项目现状判断

根据对源项目的检查，当前项目具备以下结构：

- 根目录承载核心 DB 能力，例如 `db.go`、`batch.go`、`iterator.go`、`merge.go`
- `common` 目录承载公共错误、配置和共享常量
- `data` 目录承载日志记录与数据文件逻辑
- `fio` 目录承载文件 IO 抽象与实现
- `index` 目录承载索引接口和 BTree、ART、B+Tree 实现
- `redis` 目录承载 Redis 风格数据结构封装
- `http` 目录承载 Fiber 入口与 HTTP 接口层
- `utils` 目录承载文件工具类能力
- `examples` 和 `benchmark` 目录承载示例与性能测试

当前项目还存在以下现实约束：

- 源项目 `bitcask-my` 当前是一个脏工作区
- 新目录 `kvix` 当前是一个空 git 仓库
- 用户明确要求以 `bitcask-my` 当前磁盘内容为迁移基线
- 用户明确要求本次设计、实现和文档全部使用中文表达

## 5. 重构总原则

### 5.1 先迁移，再整理

必须先将源项目内容迁移到 `kvix`，再在 `kvix` 中开展改名和重构，避免直接污染源仓库。

### 5.2 先改名，再分层

命名统一和结构整理不要混在同一个早期阶段中完成。优先先把 `bitcask-my` 改名为 `kvix`，将命名问题收敛，再进行结构拆分和注释完善。

### 5.3 优先同包拆分，避免跨包重写

本次重构的核心目标是提升可读性，而不是重写架构。因此优先采取以下策略：

- 将大文件拆成多个同包文件
- 提炼私有辅助函数
- 明确模块职责边界

尽量避免：

- 将现有逻辑大规模迁移到新包
- 将一个主题同时做语义修改和文件迁移
- 在同一批修改中同时引入新的抽象层和新行为

### 5.4 注释解释“目的”和“步骤”，不是逐行翻译

注释必须帮助读者理解：

- 函数是做什么的
- 参数为什么存在
- 当前步骤解决什么问题
- 这段流程为什么按这个顺序执行

注释不应机械重复代码表面含义。

### 5.5 文档先讲设计，再讲用法

模块 README 需要先交代：

- 模块职责
- 模块在系统中的位置
- 关键结构和核心流程
- 再说明怎么使用

这样读者才能先理解设计，再理解调用方式。

## 7. 根模块分层设计

根模块是本次重构的重点，因为当前核心流程主要集中在根目录文件中。

### 7.1 保持 `kvix` 作为核心入口包

根包仍然是系统的主要对外入口，负责暴露数据库核心能力，例如：

- 打开数据库
- 关闭数据库
- 基础读写
- 删除
- 统计
- 迭代器
- 批量写入
- Merge

### 7.2 根模块拆分策略

不改变包名，但根据职责将大文件拆为多个主题明确的文件。预期会整理为以下方向：

- `db_open.go` 或等价文件：负责数据库打开、恢复、启动阶段检查
- `db_write.go` 或等价文件：负责写路径、删除路径、追加写逻辑
- `db_read.go` 或等价文件：负责 Get、Fold、ListKeys 等读路径
- `db_state.go` 或等价文件：负责关闭、同步、统计、备份
- `db_files.go` 或等价文件：负责数据文件切换、文件加载、IO 类型调整

最终文件名不一定完全采用上述命名，但必须满足一个原则：

- 读者看文件名就能大致知道文件负责什么主题

### 7.3 根模块拆分边界

允许做的重构：

- 提炼私有辅助函数
- 将一个函数中的步骤封装为私有函数
- 将同主题方法移动到同一个文件中
- 修正文档注释和局部排版

避免做的重构：

- 修改公开方法签名
- 改变锁粒度和锁时序
- 修改日志记录写入格式
- 修改索引更新时机
- 改变 Merge 触发策略

## 8. 子模块分层设计

### 8.1 `common` 模块

职责定位：

- 存放公共错误定义
- 存放配置项和共享常量
- 承载跨模块都需要引用的基础类型定义

整理方向：

- 统一配置说明注释
- 补清默认值含义
- 明确不同配置项在启动、写入、Merge 等流程中的作用

### 8.2 `data` 模块

职责定位：

- 承载日志记录的编码解码逻辑
- 承载数据文件的打开、读取、写入、同步、关闭
- 承载位置信息结构及序列化能力

整理方向：

- 强化 `DataFile`、`LogRecord`、`LogRecordPos` 的职责说明
- 对读取流程补充分层注释，例如“读取头部”“解析长度”“读取载荷”“校验完整性”
- 对文件名生成、Hint 文件、Merge 标记文件、序列号文件等特殊文件用途做清晰解释

### 8.3 `fio` 模块

职责定位：

- 抽象底层文件 IO 行为
- 提供标准文件 IO 与 MMap 等具体实现

整理方向：

- README 解释为什么需要 IO 抽象层
- 明确上层模块如何依赖 `IOManager`
- 补充标准 IO 与 MMap 在启动和运行期的角色差异说明

### 8.4 `index` 模块

职责定位：

- 定义统一索引接口
- 提供 BTree、ART、B+Tree 等不同索引实现

整理方向：

- README 解释为什么索引要抽象为 `Indexer`
- 明确 `Put/Get/Delete/Iterator/Close` 的职责边界
- 解释不同索引实现的适用特点
- 说明哪些行为属于内存索引，哪些行为依赖磁盘结构

### 8.5 `redis` 模块

职责定位：

- 在底层 KV 引擎之上提供 Redis 风格的数据结构语义

整理方向：

- 保持一个包，不进行激进拆包
- 强化元数据、编码、过期、类型约束的职责表达
- 对 `string/hash/list/set/zset` 分别补足模块内说明
- README 重点阐明“元数据 + 子键编码”的设计思路和使用方式

### 8.6 `http` 模块

职责定位：

- 提供基于 Fiber 的 HTTP 入口和路由组织方式
- 演示数据库能力的 HTTP 暴露方式

整理方向：

- 继续保持 `main` 包形态
- 梳理 `app`、`routes`、`handler`、`dto`、`response`、`errors` 等文件边界
- README 解释启动方式、路由组织方式、错误处理方式

### 8.7 `utils` 模块

职责定位：

- 提供与业务逻辑弱相关的通用工具函数

整理方向：

- 保持工具属性，不将业务判断迁入该模块
- 对文件复制、目录大小计算等能力给出明确说明

### 8.8 `examples` 与 `benchmark`

职责定位：

- `examples` 用于展示典型使用方式
- `benchmark` 用于性能测试和对比分析

整理方向：

- 为每个目录补 README
- 让读者明确示例入口和基准测试的使用方法

## 9. 注释规范设计

### 9.1 函数级注释标准

所有核心函数和公开函数都需要使用中文注释，并至少覆盖以下内容：

- 函数用途
- 参数含义
- 返回值含义
- 关键副作用或前置条件

示例格式：

```go
// Open 打开 kvix 数据库实例，并在启动阶段完成数据文件恢复与索引重建。
// 参数:
//   - options: 数据库启动配置，包含目录、索引类型、同步策略等。
// 返回:
//   - *DB: 初始化完成后的数据库实例。
//   - error: 初始化过程中出现的错误。
func Open(options Options) (*DB, error) {
}
```

### 9.2 函数内部步骤注释标准

对于中长函数，需要按照“逻辑目的”组织内部注释，采用编号层级形式，例如：

```go
// 1. 校验启动配置，避免非法参数进入后续流程。
// 1.1 检查目录配置。
// 1.2 检查索引类型和文件阈值。
//
// 2. 准备运行环境。
// 2.1 创建数据目录。
// 2.2 尝试获取目录文件锁。
//
// 3. 加载历史状态。
// 3.1 加载 merge 遗留文件。
// 3.2 加载数据文件。
// 3.3 重建索引。
```

要求如下：

- 注释描述“步骤的目的”，不是重复代码字面意思
- 一个编号块只解释一个逻辑目标
- 子编号只在确有必要的情况下使用
- 简短函数不强制添加过多编号，避免注释噪声

### 9.3 结构体与字段注释标准

对于关键结构体，需要说明：

- 结构体代表什么概念
- 各字段承担什么角色
- 哪些字段只在特定阶段使用

例如 `DB`、`DataFile`、`RedisDataStore`、索引实现结构体等都应具备清晰注释。

## 10. README 设计规范

### 10.1 根目录 README

根目录 `README.md` 应至少包含：

- 项目简介
- 核心特性
- 目录结构总览
- 快速开始
- 基本示例
- 核心设计说明
- 测试方式

### 10.2 模块 README 通用模板

每个核心模块的 `README.md` 应至少包含：

- 模块职责
- 设计思路
- 关键文件与关键类型
- 核心流程
- 对外使用方式
- 与其他模块的关系
- 测试或验证方式

### 10.3 文档语言要求

所有文档完全使用中文，术语允许保留必要英文原名，例如：

- `WriteBatch`
- `Merge`
- `Iterator`
- `BTree`
- `Fiber`

但解释必须用中文完成。

## 13. 风险与控制措施

### 13.1 命名调整导致编译错误

风险：

- 批量改名后可能出现 import 漏改或包名不一致

控制措施：

- 改名阶段只做命名相关修改
- 改名完成后立即编译和测试

### 13.2 文件拆分导致行为顺序变化

风险：

- 提炼辅助函数或拆文件时，可能无意改变调用顺序、锁顺序或错误返回路径

控制措施：

- 优先做同包内挪动
- 保留原有执行顺序
- 每次只处理一个主题文件
- 整理后立即测试

### 13.3 文档补充反向暴露结构不清问题

风险：

- 在写 README 过程中可能发现模块边界依旧混杂

控制措施：

- 仅做与文档表达直接相关的小范围整理
- 不借文档补写的机会扩张重构范围

### 13.4 源仓库脏工作区带来基线不确定性

风险：

- 当前源项目存在未提交内容，迁移后可能难以区分哪些是历史内容、哪些是本次重构新增

控制措施：

- 先在 `kvix` 中建立明确的迁移基线
- 后续所有重构都基于 `kvix` 的独立提交历史推进
