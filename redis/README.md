# Redis 模块设计说明

## 1. 模块目标

本模块的目标是在当前 `kvix` 的 KV 存储引擎之上，构建一层接近 Redis 命令语义的数据结构层。第一阶段支持以下五种核心数据类型：

- `string`
- `hash`
- `list`
- `set`
- `zset`

第一阶段的重点不是实现完整的 Redis 协议服务，而是在 Go 代码内部提供一套接近 Redis 使用习惯的接口，例如：

- `SET` / `GET`
- `HSET` / `HGET`
- `LPUSH` / `LPOP`
- `SADD` / `SMEMBERS`
- `ZADD` / `ZRANGE`

也就是说，这一层更像是“Redis 风格的数据结构引擎”，而不是“兼容 Redis 网络协议的服务端”。

## 当前实现状态

当前仓库已经落地并通过测试的命令如下：

- `string`: `SET` `GET` `DEL` `EXPIRE` `TTL`
- `hash`: `HSET` `HGET` `HDEL` `HEXISTS` `HLEN`
- `list`: `LPUSH` `RPUSH` `LPOP` `RPOP` `LLEN` `LRANGE`
- `set`: `SADD` `SREM` `SISMEMBER` `SCARD` `SMEMBERS`
- `zset`: `ZADD` `ZREM` `ZSCORE` `ZCARD` `ZRANGE`

当前对外是 Go API，不是 Redis 协议服务端。

## 2. 设计原则

为了让这一层能够稳定地落在当前 Bitcask 风格的底层存储上，模块设计遵循以下原则：

### 2.1 尽量复用现有 KV 能力

底层 `DB` 已经具备以下核心能力：

- 单键写入：`Put`
- 单键读取：`Get`
- 单键删除：`Delete`
- 批量原子写入：`WriteBatch`
- 键遍历：`ListKeys` / `Fold`

因此 Redis 模块不重新发明底层存储，而是在此基础上做：

- 键编码
- 元数据管理
- 类型约束
- 过期控制
- 复合结构的组织与查询

### 2.2 接近 Redis 语义，但不盲目照搬全部实现细节

本模块追求“接近 Redis 命令语义”，但不会在第一阶段强行复制 Redis 内部复杂实现。例如：

- 不要求完全兼容 Redis 网络协议
- 不要求完全一致的底层时间复杂度
- 不要求一开始就覆盖所有边界命令

第一阶段优先实现“行为可理解、接口可扩展、数据可持久化”的核心子集。

### 2.3 适配追加写存储引擎

底层存储是 Bitcask 风格，天然适合：

- 追加写
- 更新覆盖
- 惰性清理

但不适合频繁做“大范围原地修改”或“删除整个集合时立刻扫描清理所有子项”。因此本模块必须避免重度依赖全量扫描删除，而是通过版本号和惰性失效来控制旧数据。

### 2.4 类型信息必须显式维护

Redis 的一个关键语义是“同一个 key 在任一时刻只能对应一种数据类型”。因此本模块必须显式保存 key 的类型元信息，并在访问时做严格校验。

例如：

- 对 `string` key 执行 `HSET` 必须报类型错误
- 对 `list` key 执行 `GET` 也必须报类型错误

## 4. 总体架构

Redis 模块采用“元数据 + 子键编码”的设计方案。

每一个 Redis 逻辑 key，在底层并不是单纯映射成一个 KV，而是被拆成两层：

1. 元数据键
2. 数据子键

其中：

- 元数据键负责描述这个逻辑 key 的全局状态
- 数据子键负责保存该 key 对应的数据内容

这种结构的核心优势是：

- 能支持多种数据类型共存
- 能统一处理 TTL 和类型检查
- 能为复杂结构保存长度、版本等必要信息
- 能利用版本号实现旧数据的逻辑失效

## 5. 键空间布局

### 5.1 元数据键

每个逻辑 key 都有一条元数据记录，逻辑格式如下：

```text
meta:<key>
```

例如：

```text
meta:user:1001
meta:order:list
meta:rank:game
```

元数据键的 value 保存该逻辑 key 的元信息，例如：

- 数据类型
- 过期时间
- 当前版本号
- 元素个数
- `list` 的头尾下标

### 5.2 数据子键

不同数据类型的数据子键逻辑格式不同，但都统一携带版本号。格式如下描述的是“逻辑结构”，不是最终落盘的原始字节。

实际实现里，为了避免 `:` 分隔符碰撞、保证范围扫描排序稳定，底层键采用了：

- 前缀
- `0x00` 分隔
- 长度前缀
- 固定宽度版本号/索引/分值编码

因此下面这些格式更适合用来理解结构，而不是理解最终字节布局。

#### String

`string` 不拆子键，直接将值保存在 `meta:<key>` 对应的 value 中，或者保存在元数据值中的固定字段区间内。

第一阶段更推荐采用“元数据与实际值一体编码”的方式，原因如下：

- `string` 只有单值，没有子元素
- 读写路径最短
- `SET` / `GET` 逻辑最简单

#### Hash

```text
hash:<key>:<version>:<field>
```

例如：

```text
hash:user:1001:3:name
hash:user:1001:3:age
```

这里的 `3` 是版本号，表示这些 field 属于 `user:1001` 当前第 3 版的 hash 数据。

#### List

```text
list:<key>:<version>:<index>
```

例如：

```text
list:task:queue:2:-1
list:task:queue:2:0
list:task:queue:2:1
```

`list` 的关键点是维护逻辑下标，而不是依赖连续物理空间。元数据中保存 `head` 和 `tail`，每次左推右推只是移动边界并写入新的索引项。

#### Set

```text
set:<key>:<version>:<member>
```

例如：

```text
set:tags:9:go
set:tags:9:redis
set:tags:9:bitcask
```

值部分可以是固定占位内容，例如 `1`，因为 `set` 的重点是成员是否存在。

#### ZSet

`zset` 需要同时支持：

- 通过 member 查 score
- 按 score 有序范围查询

因此建议维护两套子键。

第一套：成员到分值

```text
zset:dict:<key>:<version>:<member>
```

第二套：排序索引

```text
zset:score:<key>:<version>:<score编码>:<member>
```

例如：

```text
zset:dict:rank:game:4:alice
zset:dict:rank:game:4:bob
zset:score:rank:game:4:0000000012.500000:alice
zset:score:rank:game:4:0000000098.000000:bob
```

这里的 `score编码` 必须保证字符串比较顺序与 score 数值顺序一致，否则无法稳定支持范围遍历。

## 6. 为什么必须引入版本号

版本号是这个设计的关键。

### 6.1 版本号解决的问题

当一个复杂 key 被删除、过期或被其他类型覆盖时，如果我们试图立即删除所有历史子键，会遇到以下问题：

- 需要全量扫描，代价高
- 底层存储是追加写，不适合频繁做集合级清理
- 删除流程复杂，容易产生中间态

因此模块采用“逻辑删除优先”的策略。

### 6.2 版本号的工作方式

假设当前有一个 key：

```text
list:jobs
```

其当前版本为 `7`，对应的元数据为：

```text
meta:jobs -> type=list, version=7
```

此时所有有效数据都写在：

```text
list:jobs:7:<index>
```

如果执行：

- `DEL jobs`
- `jobs` 过期
- `SET jobs xxx` 导致类型从 `list` 变成 `string`

并不需要立刻扫描删除所有 `list:jobs:7:*` 子键。只需要：

- 删除或重写 `meta:jobs`
- 新建更高版本，例如 `version=8`

之后读操作只认当前元数据所指向的版本。旧版本 `7` 的子键虽然仍然存在于底层文件中，但对逻辑层来说已经失效。

### 6.3 版本号的收益

- 删除复杂结构时开销更低
- 更适合 Bitcask 的追加写模型
- 降低批量删除子键的复杂度
- 为过期和覆盖写提供统一失效机制

## 7. 元数据模型设计

每个逻辑 key 对应一条元数据记录，其 value 建议采用自定义二进制编码，而不是 JSON。

原因如下：

- 二进制更紧凑
- 编解码成本更低
- 字段布局可控
- 后续扩展兼容性更好

### 7.1 元数据字段

第一阶段建议包含以下字段：

- `Type uint8`
- `ExpireAt int64`
- `Version uint64`
- `Size uint32`
- `Head int64`
- `Tail int64`

### 7.2 字段含义

#### Type

表示逻辑 key 的数据类型，建议用枚举值表示：

- `1 = string`
- `2 = hash`
- `3 = list`
- `4 = set`
- `5 = zset`

#### ExpireAt

过期时间，使用 UnixNano 时间戳。

- `0` 表示永不过期
- 大于 `0` 表示到达该时刻后视为过期

#### Version

当前逻辑 key 的版本号，用于隔离历史子键。

#### Size

当前 key 的逻辑元素个数。

说明：

- `string` 可以固定为 `1`
- `hash` 表示 field 数量
- `set` 表示 member 数量
- `zset` 表示 member 数量
- `list` 表示元素数量

#### Head / Tail

仅 `list` 使用，用于表示当前链表逻辑边界。

例如：

- 初始空列表：`head = 0, tail = -1`
- `LPUSH` 时先 `head--` 再写入
- `RPUSH` 时先 `tail++` 再写入

是否采用上述边界约定，可以在实现时微调，但总体思想不变：通过双端游标来避免大量搬移元素。

## 8. 统一访问流程

所有 Redis 命令在真正访问数据前，都应先走元数据读取流程。

统一流程如下：

1. 计算元数据键 `meta:<key>`
2. 读取元数据
3. 若不存在，则视为 key 不存在
4. 若已过期，则执行惰性过期处理
5. 检查类型是否匹配
6. 基于当前版本去读写实际子键

这个流程是整个 Redis 模块最核心的行为入口，所有命令都应尽可能复用。

## 9. 过期策略设计

### 9.1 第一阶段采用惰性过期

第一阶段不做主动定时扫描删除，而采用惰性过期。

也就是只有在以下时机访问 key 时，才检查是否过期：

- `GET`
- `HGET`
- `LLEN`
- `SISMEMBER`
- `ZRANGE`
- `TTL`
- 其他任何命令入口

### 9.2 惰性过期处理流程

若发现 key 已过期，则：

1. 删除元数据键，或将其视为失效
2. 不立即全量删除旧子键
3. 后续如果该 key 被重新创建，使用新的版本号

这样做的原因是：

- 简化实现
- 减少后台任务复杂度
- 更适合当前存储结构

### 9.3 TTL 语义

`TTL` 应返回接近 Redis 的语义：

- key 不存在：返回不存在标识
- key 存在但没有过期时间：返回永久
- key 存在且设置了过期：返回剩余秒数或毫秒数

具体使用秒还是毫秒，可在接口层明确约定。第一阶段建议对外以 `time.Duration` 或秒级整数表达，内部统一用 `UnixNano` 存储。

## 10. 各数据结构的设计思路

### 10.1 String

`string` 是最简单的数据类型。

建议行为：

- `SET key value`：写入新的字符串值
- `GET key`：读取字符串值
- `EXPIRE key ttl`：修改元数据中的过期时间
- `DEL key`：删除元数据，使当前值失效

如果原 key 原本是其他类型，`SET` 应覆盖原值并建立新的 `string` 元数据。

### 10.2 Hash

`hash` 的本质是“field -> value”的映射。

设计方法：

- 元数据保存总字段数
- 每个 field 作为一个独立子键存储

关键命令语义：

- `HSET`：字段不存在时新增，存在时覆盖
- `HGET`：读取单个字段
- `HDEL`：删除字段，并更新字段数
- `HEXISTS`：判断字段是否存在
- `HLEN`：读取字段数量

注意点：

- `HSET` 覆盖已有字段时，`Size` 不应增加
- `HDEL` 删除不存在字段时，应保持幂等

### 10.3 List

`list` 需要支持双端插入、双端弹出和区间读取。

设计方法：

- 元数据中保存 `head` / `tail` / `size`
- 每个元素按逻辑索引落到一个子键

关键命令语义：

- `LPUSH`：在头部插入一个或多个元素
- `RPUSH`：在尾部插入一个或多个元素
- `LPOP`：弹出头部元素
- `RPOP`：弹出尾部元素
- `LLEN`：返回列表长度
- `LRANGE`：按逻辑顺序返回区间元素

这个方案不要求列表元素在底层物理位置连续，只要求逻辑索引连续即可。

### 10.4 Set

`set` 的本质是无序去重集合。

设计方法：

- 每个 member 作为一个独立子键
- value 可为固定占位值

关键命令语义：

- `SADD`：新增成员，重复成员不重复计数
- `SREM`：删除成员
- `SISMEMBER`：判断成员是否存在
- `SCARD`：返回元素个数
- `SMEMBERS`：返回全部成员

注意点：

- `SADD` 的返回值应体现实际新增数量
- `SREM` 对不存在成员应幂等

### 10.5 ZSet

`zset` 是第一阶段最复杂的数据结构，因为它同时要求：

- 通过 member 查 score
- 按 score 做排序读取

设计方法：

- 一套字典索引：`member -> score`
- 一套排序索引：`score -> member`

关键命令语义：

- `ZADD`：新增或更新成员分值
- `ZREM`：删除成员
- `ZSCORE`：查询成员分值
- `ZCARD`：返回成员数量
- `ZRANGE`：按分值从小到大返回范围成员

注意点：

- `ZADD` 更新已有 member 的 score 时，必须删除旧排序索引，再写入新排序索引
- `ZRANGE` 的实现会依赖底层键遍历与前缀过滤能力

## 11. 类型错误处理

Redis 一个非常重要的行为是严格区分数据类型。

例如：

- `SET name "alice"` 之后，再执行 `HSET name age 18` 应报错
- `LPUSH users a b` 之后，再执行 `GET users` 也应报错

因此模块需要定义统一的类型错误，例如：

```text
WRONGTYPE Operation against a key holding the wrong kind of value
```

在 Go 层可以表现为一个固定错误变量，供上层识别。

## 12. 原子性设计

复合结构操作通常不止写一个底层 KV，因此需要借助现有的 `WriteBatch` 能力。

适合用批量原子写入的场景包括：

- `HSET` 同时写 field 和更新元数据
- `LPUSH` 同时写元素和更新 `head/size`
- `SADD` 同时写 member 和更新计数
- `ZADD` 同时写字典索引、排序索引和元数据

原则上，只要一个 Redis 命令需要同时更新多条底层记录，就应该优先使用批量提交，避免产生中间态。

## 13. 删除策略

### 13.1 逻辑删除优先

删除一个 key 时，优先删除或失效其元数据，而不是立即清理所有子键。

### 13.2 旧数据可交由后续机制回收

旧版本子键虽然仍会残留在底层文件中，但：

- 不会再被逻辑层读取
- 可以在后续迭代中结合 merge 或 compaction 逐步回收

这与 Bitcask 的存储哲学是一致的。

## 14. 接口层设计建议

为了实现“接近 Redis 命令语义的一层接口”，建议在模块中暴露两层 API：

### 14.1 数据结构方法层

例如：

- `Set`
- `Get`
- `HSet`
- `HGet`
- `LPush`
- `SAdd`
- `ZAdd`

这一层面向 Go 代码直接调用，是最主要的实现层。

### 14.2 命令风格封装层

可以进一步封装成接近 Redis 命令风格的统一入口，例如：

- `Do("SET", "k", "v")`
- `Do("HSET", "user", "name", "tom")`

或者先不做字符串分发，而是通过更贴近 Redis 命名的导出方法提供能力。

第一阶段建议优先完成“方法级命令语义”，即：

- 方法名接近 Redis
- 参数和返回值尽量保持直观
- 错误语义清晰

## 15. 编码与注释规范

- 核心注释使用中文

- 与底层 merge/compact 的联合回收策略

## 18. 总结

本模块的核心思路可以概括为一句话：

在 Bitcask 风格的底层 KV 存储上，通过“元数据 + 版本化子键”的方式，构建一层接近 Redis 命令语义的数据结构抽象。

这个设计的关键价值在于：

- 保留底层 KV 引擎的简单性
- 统一管理类型、TTL 和结构元信息
- 通过版本号适配追加写存储模型
- 为 `string/hash/list/set/zset` 提供可扩展的实现基础

第一阶段不追求一次性实现完整 Redis，而是先建立清晰、稳定、可演进的内部结构。在这个基础上，后续无论是扩展命令集，还是进一步做协议层，都会更容易推进。
